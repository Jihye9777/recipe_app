# 레시피 추출 품질 개선 설계

상태: 사용자 확인 대기. 사용자가 승인한 다섯 항목을 구현 가능한 설계로 구체화한 문서이며, 아직 제품 코드는 변경하지 않았다.

## 목적과 완료 조건

모델 교체보다 수집 근거와 검증을 개선한다. 자막만으로 빠진 재료·수량·조리 과정을 보완하되, 근거가 부족한 결과를 정확하다고 표시하지 않는다.

1. YouTube 자막과 설명란을 함께 수집하고 출처를 보존한다.
2. 로컬 Ollama 모델로 주요 화면에 실제 표시된 글씨를 읽는다. 보이지 않는 내용은 추측하지 않는다.
3. 재료 누락, 수량 충돌, 단계에만 있는 재료, 실질적 조리 단계 부재를 검사한다.
4. 수집 실패·읽기 불가·출처 충돌은 사용자 검토로 보낸다.
5. 기존 세 영상은 별도 평가 저장소에서 재처리한다. 현재 저장된 레시피는 덮어쓰지 않는다.

## 변경 범위와 제한

- 기존 FastAPI, LangGraph, SQLite 원본 DB, Qdrant Local, Ollama 구성을 유지한다.
- yt-dlp, 유료 AI, 클라우드 추적, 자동 모델 다운로드를 추가하지 않는다.
- 자막 API → pytubefix/로컬 Whisper 폴백과 직접 텍스트 입력을 유지한다.
- 기존 레시피·작업·체크포인트·벡터 인덱스를 초기화하지 않는다.
- 신규 패키지 설치, 파일 삭제, 추가 커밋·push는 별도 승인 없이 실행하지 않는다.
- `.env`와 인증 파일을 읽거나 수정하지 않는다.
- 모델의 출력은 검증된 사실이 아니다. 자동 검사는 정확도 보증이나 알레르기 안전 인증으로 표시하지 않는다.

## 선택한 방식

자막만 재프롬프팅하는 방식은 화면에만 있는 정보의 누락을 해결하지 못한다. 전체 영상을 다운로드하고 모든 프레임을 분석하는 방식은 실행 시간·디스크·추가 도구 부담이 크다.

이번에는 **자막 + 설명란 + 제한된 스토리보드 화면 수집**을 기존 수집 그래프에 추가한다. 기존 requests와 Ollama 이미지 입력을 사용하며, 추가 이미지 패키지를 전제하지 않는다. 스토리보드는 저해상도 미리보기이므로 글씨를 못 읽는 경우가 있다. 그 경우 성공으로 간주하지 않고 검토 사유를 남긴다. 원본 영상 전체를 분석했다고 표시하지 않는다.

## 수집과 근거 모델

새 `sources.py`가 YouTube 메타데이터·설명란·스토리보드 수집을 담당한다. 기존 자막 추출 함수는 재사용한다.

수집 결과는 버전형 `source_bundle` 사전으로 전달한다.

- `version`: `recipe-sources-v1`.
- `video_id`, `title`: 검증한 영상 ID와 원본 제목.
- `sources`: 출처별 `id`, `kind`(caption/description/frame/manual), `text`, 원본 영상 URL, 가능한 시각 정보.
- `observations`: 화면에서 읽은 재료명·분량·단위와 정확한 인용문, 연결된 출처 ID. 판독 불가한 값은 null.
- `warnings`: 설명란 수집 실패, 화면 미지원, 타임아웃, 판독 불가, 샘플 범위 제한 등.
- `coverage`: 샘플링된 화면이라는 사실과 수집 범위. 전체 영상 검증 여부는 false.

빈 설명란은 정상적인 빈 결과다. 설명란을 가져오지 못한 것과 구별한다. 자막이 실패해도 설명란이나 화면의 사용 가능한 근거가 있으면 작업을 이어가되 검토 사유를 유지한다. 아무 근거도 없으면 명확한 오류로 종료한다.

수집 텍스트는 종류·출처 ID·시각을 붙여 모델에 제공한다. 광고·채널 소개를 재료 목록이라고 가정하지 않는다. 외부 텍스트와 이미지 속 지시는 데이터로만 취급한다.

## 화면 읽기

- 실행 중인 Ollama 모델의 이미지 지원 여부를 확인한다. 미지원이면 모델을 설치하거나 교체하지 않고 검토 대상으로 남긴다.
- YouTube 플레이어의 스토리보드에서 시간 간격이 있는 레벨을 선택한다. 영상의 여러 구간을 포함하도록 최대 6개 시트를 고른다. 각 시트와 타일의 시각 매핑을 함께 제공한다.
- 모델에는 실제로 보이는 재료·수량·조리 지시만 전사하도록 요구한다. 음식의 외형, 일반 레시피 상식, 잘린 글씨로 빈칸을 채우지 않는다.
- 인용문과 판독 가능 여부를 JSON Schema로 받는다. 스키마 오류·빈 판독·중요한 글씨 판독 불가·요청 실패는 검토 사유다.
- 각 HTTP 요청에 연결·읽기 타임아웃을 적용하고 응답 크기를 제한한다. 스토리보드가 없거나 제한 내에서 확보되지 않으면 실패를 보존한다.
- 스토리보드 URL은 HTTPS의 허용된 YouTube 이미지 호스트만 사용한다. 사용자 입력이나 설명란의 임의 URL은 내려받지 않으며 리다이렉트도 같은 정책으로 검사한다.

## 구조화와 품질 검사

`integrations.py`의 Ollama 어댑터에 이미지 전사 호출을 추가한다. 기존 레시피 구조화는 종류가 구분된 모든 근거를 받도록 프롬프트를 보완한다. 원문 인용과 출처 연결은 `source_bundle` 및 검사 결과에 보존하며 기존 Recipe 필드를 불필요하게 바꾸지 않는다.

`domain.py`의 검사를 다음과 같이 확장한다.

- 재료의 근거 인용이 수집 출처에 실제 존재하는지 검사한다.
- 명시적으로 식별된 근거 재료와 최종 재료 목록을 비교해 누락 후보를 찾는다. 모호한 일반 단어를 재료로 확정하지 않는다.
- 분수 `½`, `1/2`, 소수 `0.5`는 비교 가능하게 처리하되, 단위가 다르거나 생략됐으면 임의 환산하지 않는다.
- `스푼`은 그대로 보존한다. 큰술·작은술이라고 추정하거나 단위를 삭제하지 않는다.
- 같은 재료의 서로 다른 명시적 수량, 재료 목록과 단계의 수량 충돌을 검토 사유로 남긴다. 출처 우선순위만으로 충돌을 숨기지 않는다.
- 단계에 등장하는 식별 가능한 재료가 재료 목록에 없으면 검토한다. 선택 재료·고명도 근거가 있으면 구별해 보존한다.
- 시식 평가, “조리 과정이 없다”는 문장만 있는 결과는 정상 조리 단계로 통과시키지 않는다.

예시 회귀 검사는 식초 누락, 참기름 ½스푼을 1스푼으로 변경, 식초 1.5스푼인데 단계에서 모두 1스푼으로 지시, 단계에만 있는 대패삼겹살, 시식 설명만 있는 조리 단계를 포함한다. 특정 영상 ID에 맞춘 예외 처리는 만들지 않는다.

## LangGraph와 검토 대기

기존 URL 검증·중복 확인 다음에 근거 수집과 화면 읽기를 연결하고, 이후 전처리 → 구조화 → 정규화·검사 → 최대 1회 재검토 → 사용자 확인 흐름을 유지한다.

수집 경고와 레시피 품질 문제는 별도로 보존한다. LLM 재시도에서 레시피 형식이 좋아졌다는 이유로 화면 수집 실패나 출처 충돌이 사라지면 안 된다. 해결되지 않은 문제가 있으면 저장 전에 기존 LangGraph interrupt로 검토 대기에 들어간다.

기존 체크포인트에 새 필드가 없을 수 있다. 누락을 빈 값으로 안전하게 처리하되, 수집하지 않은 출처를 확인 완료로 표시하지 않는다. 직접 붙여 넣은 텍스트에는 영상 수집·화면 읽기를 강제하지 않는다.

## 저장과 화면

`storage.py`에 `recipes.sources` JSON 열을 보존형 마이그레이션으로 추가한다. 기존 행은 빈 객체로 남기며 원문·레시피 JSON을 수정하지 않는다. 신규 저장 시 근거 묶음과 출처별 검사 결과를 함께 저장한다. 프레임 이미지 base64를 레시피 DB나 API 응답에 넣지는 않는다.

검토 화면에는 수집 출처, 화면 판독 한계, 충돌·누락 사유를 표시한다. 기존 JSON 수정·승인 기능과 개별/선택 삭제는 유지한다. 저장된 새 레시피에서도 출처 정보를 확인할 수 있게 한다. 기존 레시피에는 근거 수집 정보가 없다는 사실을 표시하고 수집했다고 소급 표기하지 않는다.

## 검증과 기존 3개 재평가

1. 단위·분수·누락·모순·조리 단계 검사에 실패 재현 테스트를 먼저 작성한다.
2. 수집기에는 빈 설명란, 요청 실패, 잘못된 플레이어 JSON, 스토리보드 URL 검증, 응답 크기 제한 테스트를 둔다. Ollama 이미지 호출과 실패 처리는 경계에서 대체해 검사한다.
3. 그래프에는 수집 경고가 재시도 후에도 검토로 이어지는지, 텍스트 입력이 유지되는지, 사용자 승인·재개와 기존 중복 방지가 동작하는지 검사한다.
4. DB 마이그레이션은 임시 DB에서 기존 행 보존과 새 근거 저장을 검사한다. 기존 Python·DOM·일괄 삭제 테스트도 실행한다.
5. 실제 세 영상은 `.runtime/` 아래 새 평가 디렉터리의 SQLite·체크포인트·Qdrant에서 실행한다. 운영 API의 analyze나 기존 DB의 UPDATE를 사용하지 않는다. 검토 대기를 자동 승인하지 않는다.
6. 실행 전후 기존 레시피 세 건의 식별자와 내용을 읽기 전용으로 비교한다. 평가 결과에는 수집 성공 여부, 관찰한 누락·충돌, 남은 검토 사유, 모델 실행 한계를 기록한다. 단위 테스트 통과를 실제 정확도 개선으로 대신하지 않는다.

평가 산출물과 원문은 Git 무시 경로에 보관한다. 새 패키지나 모델이 꼭 필요해지면 그 작업만 멈추고 설치 범위를 설명해 승인받는다. 실제 네트워크·모델 실행 실패도 결과에 포함하고 완료했다고 숨기지 않는다.
