# 단계 근거 구현 계약

사용자는 2026-10-22 설계를 승인하고 poteto-mode로 구현, 커밋, 로컬 main 병합을 요청했다. 기존 변경의 기준선은 2e6e4c7이다. 원격 push, PR, 사용자 DB 수정은 범위 밖이다.

## 선택한 구조

설계 후보 A의 원문 사실 추출 단계와 단계별 source_step 연결을 채택한다. 후보 B의 단일 순수 검사 모듈을 결합한다. 독립 비교 검토도 A를 선택했다. 원문 사실은 재검토 중 교체하지 않으며, 저장 직전에도 새 검사 버전과 사실 존재를 확인한다.

데이터는 domain.py의 StepIngredient, CookingStep, SourceFacts와 Recipe.step_details로 표현한다. 기존 steps 문자열 목록을 유지한다. 각 CookingStep은 재료별 분량, 조리 동작, 기구, 시간 초 값, 원문 시간 표현, 정확한 인용문, 원문 단계 번호를 가진다. 재료 분량은 total, partial, unknown 관계를 보존한다. 모호한 부분량은 합산하거나 추측하지 않는다.

recipe_quality.py는 원문 인용·분량·기구·시간 검사, 원문 사실과 후보 비교, 단계 문장 생성만 담당한다. 네트워크나 DB를 호출하지 않는다. Ollama.source_facts(text)는 SourceFacts 형식의 사전을 반환하고, 기존 recipe(text, feedback='')는 선택적인 source_facts 인자를 추가한다. 기존 두 인자 호출은 유지하지만 신규 자동 저장 경로는 검증된 사실을 요구한다.

원문 사실 추출 실패와 근거 문제는 별도 source_issues로 보존한다. 모델 재검토가 후보를 교체해도 이 경고를 지우지 않는다. persist에 도달한 과거 체크포인트도 검사 자료가 없으면 사용자 검토로 보낸다. 사용자 승인은 실제 저장 후보에만 적용하며 명시적 수정 문장을 자동 문장으로 덮어쓰지 않는다.

지원되는 원문의 명시적 숫자·단위·기구·시간을 모델과 별도로 검사한다. 전자레인지와 1분 30초는 같은 원문 단계와 최종 단계에서 비교한다. 스푼과 큰술은 동등 처리하지 않는다. 인용이 없는 주장, 누락, 충돌, 연결이 불명확한 경우는 review다. 전체 한국어 문장에 대한 사실 검증이나 모델 정확도 보장은 하지 않는다.

## 구현 순서와 검증

1. 추가 타입과 순수 검사 함수의 실패 테스트를 먼저 만든다. 분수·소수, 식초 누락과 수량 변경, 기구·시간 누락, 다른 단계로 이동, 근거 없는 추가, 부분량 모호성을 확인한다.
2. 통과하는 최소 타입·검사 구현을 추가하고 해당 검사를 실행한다.
3. 모델 원문 사실 호출과 그래프 상태·검토·persist 보호를 연결한다. 오래된 레시피와 체크포인트, 재검토 1회, 실패 재개, 명시적 사용자 승인, SQLite 원본 보존을 격리 테스트한다.
4. UI에 추가 단계 근거를 안전하게 표시하고 기존 문장·JSON 검토를 유지한다. API·DOM 회귀 검사와 문서를 맞춘다.
5. 사용자 DB와 분리된 합성 원문·가능한 실제 저장 원문으로 로컬 모델을 확인한다. 원본 레시피를 덮어쓰지 않으며 실패나 미검증을 통과로 표시하지 않는다.
6. 독립 비작성자가 정확한 커밋을 검증한 뒤 로컬 main을 fast-forward한다. 보호 브랜치로 이전 main을 보존한다. 원격 push나 PR은 생성하지 않는다.

## 실행 제약과 수용한 비용

새 에이전트 생성이 세션 한도에 걸려 설계 비교는 독립 에이전트 A와 루트의 순차 후보 B로 수행했다. 독립 비작성자가 두 후보를 비교했다. 신규 구현 소유자 생성도 불가능하므로 루트가 격리 worktree의 단일 작성자가 된다. 완료된 비작성 리뷰어를 정식 followup_task로 재사용해 독립 검증은 유지한다. 병렬 탐색 수는 줄지만 자기 검토를 독립 검증으로 대체하지 않는다.

추가 로컬 모델 호출의 지연과 일부 표현에서의 보수적인 검토 대기를 수용한다. 설명란·화면 수집, 범용 언어 분석기, 새 DB, 추가 패키지는 도입하지 않는다. 원문에 없는 전자레인지나 분량을 추론해 채우지 않는다.
